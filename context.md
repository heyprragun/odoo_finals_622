# DealFlow360 — Project Context

B2B sales operations platform.
- **Backend**: Node/Express/TypeScript, Prisma ORM, PostgreSQL, JWT + bcrypt auth. Layered as routes → controllers → services → Prisma; RBAC via `authorizeRoles` middleware, resource-ownership checks in the service layer.
- **Frontend**: React + Vite, plain CSS conventions (`sales-card`, `sales-table`, `sales-btn`/`sales-btn-primary`/`sales-btn-danger`, `banner-error`/`banner-success`, `sales-empty`, `status-badge status-${status}`, `tier-badge`, `product-search-row`, `sales-actions`).

Built incrementally, one feature at a time, with the user consistently insisting on:
1. Inspecting existing code before extending it.
2. Real backend-enforced logic — never a frontend-only restriction.
3. No fake/hardcoded data.
4. Verifying everything live via the actual API/curl (or typecheck+lint+build when no browser tool is available), not just "looks right."

## Personas / Roles

- **Sales Rep** — builds quotes from customer requests, sets discounts, submits for approval.
- **Manager** — first approval gate on all quotes.
- **Finance** — second approval gate, but only for HIGH-risk quotes.
- **Admin** — master approval gate (final say on everything); also decides tier-change requests and configures discount governance.
- **Customer** (portal) — dashboard, subscriptions, invoices, creating requests, recurring plans, negotiations, tier-change requests.

## Core Workflow (established earlier, still the backbone)

Customer Request → Sales Rep builds Quote → **Manager approval** → **Finance approval** (HIGH risk only) → **Admin approval** (always, master gate) → Quote APPROVED → Subscriptions/Invoices generated → Inventory allocated per warehouse.

Race-safe status transitions everywhere use the guard pattern:
```ts
prisma.quote.updateMany({ where: { id, status: currentStatus }, data: { status: nextStatus } })
```
throwing `ApiError.conflict` (409) on a zero-row match.

Other core systems already built and verified in earlier segments (not touched this session but foundational):
- Discount governance (tier + category limits, admin-configurable).
- Inventory/warehouse allocation with editable per-warehouse splits and real reservation; stock-shortage handling ("Mark Order Not Possible").
- Groq AI integration for upsell/cross-sell recommendations and AI sales insights.
- Full Admin Reports section (team performance, quotations filtering, product performance, customer tier drill-down, PDF/XLSX export).

### 4. Discount Expectation Gate (most recent feature — now complete end-to-end)
User's request: Sales Reps couldn't see what discount the customer expected. Rule needed: if the Rep's offered discount ≥ customer's expected discount, proceed normally. If the Rep offers **less**, flag it in the customer's Negotiations tab and **block** the quote from going to Manager/Finance approval until resolved.

- Schema: `DiscountReviewStatus` enum {NONE, PENDING}; `CustomerRequest.proposedDiscountPercentage`, `CustomerRequest.discountReviewStatus`.
- `quote.service.ts`'s `submitQuote()`: gate check runs **before** the normal status transition.
  - If Rep's discount < customer's `expectedDiscountPercentage` → quote status left unchanged (still DRAFT/REVISION_REQUIRED), request flagged `PENDING`, proposed discount recorded.
  - If already flagged but the Rep's new discount now meets/exceeds the (possibly updated) expectation → flag auto-clears and submission proceeds normally.
  - Re-flagging always checks against the **latest** `expectedDiscountPercentage`, not a stale one.
- Customer portal: `listMyDiscountReviews()` / `resolveDiscountReview(requestId, newExpectedDiscountPercentage, note)` — resolving is race-safe (`updateMany` guarded on PENDING), sets a new expected discount (accepting the Rep's offer as-is, or countering), clears the flag.
- Sanitization: `sanitizeQuote.ts` exposes `customerRequestDiscountReview` (expected/proposed discount + status) to anyone who can already see the quote — no new data leakage.
- Frontend:
  - `CustomerRequestDetail.tsx` — shows the customer's expected discount to the Sales Rep.
  - `QuoteBuilder.tsx` — shows a "Customer's Discount Expectation" card; on submit, if flagged, shows a clear inline error explaining the block instead of a generic failure (submit button deliberately left enabled while PENDING, since the Rep's own legitimate fix — raising the discount and resubmitting — must still work).
  - `Negotiations.tsx` (customer) — new "Discount Review Needed" section (`DiscountReviewsSection`) above the existing quote-negotiation table: lists flagged orders (products, expected vs. offered discount), lets the customer accept-as-is (input pre-filled with the Rep's offer) or counter with a different value plus an optional note, calling `resolveDiscountReview`.
- **Fully verified live via curl** end-to-end (request with 20% expected → Rep offers 10% → blocked/flagged → customer resolves to 15% → Rep still at 10% → re-flagged against 15% → Rep raises to 15% → submits successfully, flag clears). Frontend verified via `tsc -b` / `oxlint` / `vite build` only (no browser tool available this session).

### 5. Quote Builder Lockdown + Delete Draft + (confirmed pre-existing) Manager Deny
User's request: remove the Product Search section from the Quote Builder for quotes built from a customer request, make quantities non-editable (order quantity is fixed), add a "Delete Draft" option, and let a Sales Manager deny an order with a comment the customer can see.

- **Product Search / quantity / remove — locked for request-based quotes only**: `QuoteBuilder.tsx` computes `isFromRequest = !!quote.customerRequestId` and hides Product Search, quantity edit controls, and the per-line Remove button whenever true. A quote started manually (`NewQuote.tsx`, no linked request) is unaffected — it still needs all of it since there's no request to lock to. Warehouse allocation editing is untouched either way (that's fulfillment routing, not composition).
- **Backend-enforced, not just hidden**: `quote.service.ts`'s `createQuote`/`updateQuote` now always derive product/quantity composition from the originating `CustomerRequest.items` when one exists, ignoring whatever the client sends for those fields (client-supplied `allocations` are still matched in by `productId`). Verified live: a raw API call trying to bump quantity/add/drop products on a request-based quote is silently overridden back to the request's real composition.
- **Delete Draft**: new `DELETE /api/quotes/:id` (owner Sales Rep, DRAFT status only — not REVISION_REQUIRED, which carries real history worth keeping). Releases the warehouse reservation, hard-deletes the quote (cascades items/allocations/audit entries), and flips the originating `CustomerRequest` back to `IN_REVIEW` (same mechanism `negotiateQuote` uses) so it reappears in the Rep's active queue. Verified live: delete → 404 on refetch → request shows `IN_REVIEW`/`quote: null` → a fresh quote can be created from it immediately; delete on a submitted (non-DRAFT) quote correctly 400s.
- **Manager deny-with-comment**: this already existed before this session (pre-dates this file) — `ApprovalDetail.tsx`'s "Reject" button (Manager/Finance/Admin, gated to their own stage) requires a note, and `customerPortal.service.ts` already surfaces it as `rejectionReason` on the customer's Negotiations tab. Re-verified live, nothing new built.

### 6. Deal Health (Manager + Admin)
User's request: a Deal Health page flagging 3 categories — stalled deals, discount anomalies, delivery slippage — with a flagged-deals list and a click-through detail view of what's wrong. Frontend shell already existed (`DealHealth.tsx`, placeholder/static) from an earlier session; this session built the real backend and wired it up.

- New `dealHealth.service.ts` / `.controller.ts` / `.routes.ts`, mounted at `/api/deal-health`, Manager + Admin only (unlike the Admin Reports section, Manager is included since these are exactly what a Sales Manager acts on day to day).
- No new schema — everything is computed fresh on every request from existing `Quote`/`QuoteItem`/`QuoteItemAllocation`/`QuoteAuditEntry` data, nothing stored/cached.
- **Stalled** = status still in-pipeline (`DRAFT`/`SUBMITTED`(legacy)/`REVISION_REQUIRED`/`PENDING_*_APPROVAL`) and `updatedAt` older than `STALLED_DAYS` (5).
- **Discount anomaly** = discount exceeds the *same Sales Rep's own* historical average (across all their non-DRAFT quotes, min `DISCOUNT_ANOMALY_MIN_HISTORY` (3) to trust the baseline) by more than `DISCOUNT_ANOMALY_POINTS_THRESHOLD` (15) points — deliberately relative to the Rep's own norm, distinct from the existing tier/category discount-governance risk engine (`discountGovernance.service.ts`).
- **Delivery slippage** = status `APPROVED`, `updatedAt` older than `DELIVERY_SLIPPAGE_DAYS` (3) — relies on the fact that a Quote row is never updated again once it reaches `APPROVED`, so `updatedAt` doubles as "approved at" — and at least one `QuoteItem`'s total allocated quantity is still short of what was ordered. There's no delivery/shipment model anywhere in the schema, so this is the closest real signal available; all 3 thresholds are hardcoded constants (not admin-configurable — out of scope for this ask).
- `GET /api/deal-health` → summary counts + a flat flagged-deals list (one row per quote+flagType, a quote can appear once per category it trips). `GET /api/deal-health/:quoteId` → full detail for every flag currently active on that one quote (recomputed fresh, not just the one clicked).
- Frontend: `DealHealth.tsx` rewritten from its static placeholder to consume the real endpoint (clickable rows); new `DealHealthDetail.tsx` renders per-flag-type detail (last audit entry for stalled, Rep-average comparison for anomaly, short-item table for slippage). New `flag-badge` CSS reusing the existing banner color scheme.
- **Verified live** by temporarily backdating `updatedAt`/`discountPercentage` on real demo quotes via direct SQL to trip each of the 3 conditions one at a time (confirmed in both the overview and detail endpoints, plus role-gating: SALES_REP/FINANCE 403, MANAGER/ADMIN 200), then restored every touched value back to its original. Baseline demo data currently has almost no `QuoteItemAllocation` rows on `APPROVED` quotes (only 2 of 14 items) — real, not a bug, but means once this demo data crosses the 3-day slippage threshold, most old approved demo quotes will start showing as slippage since they were seeded without simulated warehouse reservation.

### 7. Deal Health — Reject Deal / Nudge Sales Rep
User's request: on opening any flagged deal, Manager and Admin get two actions - reject the deal, or nudge the Sales Rep to update it. Clarified with the user up front: for a delivery-slippage flag (always an already-`APPROVED` quote, with live Subscriptions/Invoices already generated), "Reject" should actually cancel the whole confirmed order (subscriptions + unpaid invoices included), not just flip a status flag.

- **Schema migration** (`20260906120000_deal_health_actions`): `QuoteAuditAction` gains `MANAGER_CANCELLED` and `NUDGED`; `InvoiceStatus` gains `CANCELLED`. (`SubscriptionStatus.CANCELLED` already existed, reused as-is.)
- **`POST /api/deal-health/:quoteId/reject`** (`dealHealth.service.ts`'s `rejectFlaggedDeal`) - two entirely different operations depending on where the quote sits:
  - Still in-pipeline (`DRAFT` through `PENDING_ADMIN_APPROVAL`): ordinary rejection - status → `REJECTED`, same audit action approval.service.ts's own reject uses, reservation released. Reachable regardless of stage/owner (unlike the Approvals queue's stage-restricted reject, or quote.service.ts's owner-only editing) - a Manager/Admin can reject any Rep's deal directly from here.
  - Already `APPROVED`: full unwind. Quote → `CANCELLED` (not `REJECTED` - that's pre-approval only), every `ACTIVE`/`PAUSED` `Subscription` on the quote → `CANCELLED` with a matching `SubscriptionEvent`, every still-`UNPAID` `Invoice` → `CANCELLED` (a `PAID` one is left alone - no refund flow exists), reservation released, and if it came from a `CustomerRequest`, that flips to `CANCELLED` too.
  - A quote already `REJECTED`/`CANCELLED` 400s ("already closed").
- **`POST /api/deal-health/:quoteId/nudge`** (`nudgeSalesRep`) - advisory only, logs a `NUDGED` audit entry, never touches status (so nudging alone can't clear a STALLED flag - only the Rep actually updating the quote does that).
- **Nudge visibility**: `quote.service.ts`'s `QUOTE_INCLUDE` now pulls the single latest `NUDGED` entry; `sanitizeQuote.ts` exposes it as `pendingNudge` only while it's still "unread" - i.e. its `createdAt` is newer than the quote's own `updatedAt`. Free to compute (creating an audit entry never bumps the parent Quote's `updatedAt`), and means the banner auto-clears the moment the Rep saves/submits the quote again. Shown in `QuoteBuilder.tsx` regardless of quote status (works for a still-`DRAFT` stalled deal, unlike `QuoteAuditTrail`/`getApprovalDetail` which only cover quotes that have entered the approval workflow).
- **Customer-facing cancellation reason**: `customerPortal.service.ts`'s `formatOrderListItem` exposes `cancellationReason`, sourced from the quote's latest audit entry, but *only* when that entry's action is `MANAGER_CANCELLED` - a customer's own `CUSTOMER_CANCELLED` (via the existing Cancel Order action) stays silent since they already know why. Rendered on `CustomerOrderDetail.tsx`.
- Frontend: `DealHealthDetail.tsx` gets a "Decision" card (Reject Deal / Nudge Sales Rep, mirroring `ApprovalDetail.tsx`'s pending-action + required-note pattern), shown whenever the deal still has active flags.
- **Fully verified live**: (1) nudge a backdated-stalled quote → confirmed the owning Rep sees `pendingNudge` on their own quote fetch → confirmed it clears once the quote's `updatedAt` moves past it; (2) reject that same still-`PENDING_MANAGER_APPROVAL` quote → `REJECTED`, customer's Negotiations tab shows the reason, re-rejecting 400s; (3) built a full recurring order through real Customer→Sales Rep→Manager→Admin approval to get a genuine `APPROVED` quote with a real `ACTIVE` Subscription + `UNPAID` Invoice, rejected it via Deal Health → confirmed quote/subscription/invoice/customer-request all correctly `CANCELLED`, `SubscriptionEvent` logged, and the customer's own order detail shows the `cancellationReason`. All test fixtures cleaned up afterward (SQL, respecting FK order: subscription_events → invoices → subscriptions → quotes → customer_requests).

### 8. Customer Subscription Detail — Cancel / Change Plan
User's request: from the customer portal's subscription list, clicking a subscription should show its details plus options to cancel or modify it. Cancellation must be visible to every internal role. A modification ("change plan" - Monthly/Quarterly/Annually) must go through the *same pipeline as any standard order* rather than being an instant self-service change.

- **Schema migration** (`20260906140000_subscription_plan_change`): `CustomerRequest.modifiesSubscriptionId` (nullable FK → `Subscription`), plus the reverse `Subscription.planChangeRequests` relation.
- **List/detail broadened**: `listMySubscriptions` (was `listMyActiveSubscriptions`) now returns every status, not just `ACTIVE`, so a cancelled/paused subscription's history stays reachable. New `GET /portal/subscriptions/:id` (`getMySubscriptionDetail`) returns full detail + event history + `cancellable`/`modifiable`/`pendingPlanChange` flags (`modifiable` is false while an unresolved plan-change request already exists against it - `hasPendingPlanChange` walks every `CustomerRequest` referencing this subscription and checks whether its linked quote, if any, has reached a terminal status yet).
- **Cancel** (`POST /portal/subscriptions/:id/cancel`, `cancelMySubscription`): ownership-checked, then calls the *same* `subscription.service.ts` `cancelSubscription` Finance/Admin already use internally - just with a `"Cancelled by customer: ..."` note. This is what makes "all roles aware" true for free: the existing shared `/api/subscriptions` list and `/api/subscriptions/company/:customerId` detail (visible to SALES_REP/MANAGER/FINANCE/ADMIN) already show live status + full event history with that note - no new notification plumbing needed, verified live.
- **Change Plan is not a direct mutation** - it's the *exact same* `createMyRequest` (`Create Request → Quote → Manager/Finance/Admin approval`) flow `RecurringPlans.tsx` already uses for a brand-new recurring order, just with `modifiesSubscriptionId` set. `createMyRequest` backend-enforces (never trusts the frontend): items must be exactly `[{productId, quantity}]` matching the subscription being modified (only the billing cycle may differ from its current one), the subscription must be this customer's own `ACTIVE` one, and no other unresolved plan-change request can already be in flight against it.
- **Completing the swap**: `subscription.service.ts`'s `createSubscriptionsForApprovedQuote` (already the single place that turns an `APPROVED` quote into real `Subscription` rows) now first checks `quote.customerRequest?.modifiesSubscriptionId` - if set, cancels that old subscription (guarded on still `ACTIVE`/`PAUSED`, so idempotent) with a `SubscriptionEvent` cross-referencing the new quote's number, *before* creating the fresh one on the new cycle. Same transaction as the rest of approval - no separate step, no way for the old one to survive alongside the new one.
- Sales Rep visibility: `customerRequest.service.ts`'s `getCustomerRequestById` now includes `modifiesSubscription`; `CustomerRequestDetail.tsx` shows a clear banner ("this is a plan change request for subscription X, currently billed Y") so the Rep understands why the item/quantity look pre-filled and locked (the prior session's request-based-quote lockdown already prevents them from being changed anyway).
- Frontend: `CustomerSubscriptions.tsx` rows are now clickable (`/portal/subscriptions/:id`); new `CustomerSubscriptionDetail.tsx` shows stats + event history + inline Cancel and Change Plan forms (mirroring `CustomerOrderDetail.tsx`'s/`RecurringPlans.tsx`'s existing patterns exactly).
- **Fully verified live** against two of the demo customer's real subscriptions (temporarily mutated, then fully reverted via SQL): (1) direct cancel → confirmed visible with the right note in both the customer's own view and the Sales Rep's shared Subscriptions view; (2) full plan-change pipeline - validation rejects a mismatched quantity, a same-cycle request, and a second concurrent request; a valid request creates a `CustomerRequest` the Sales Rep can see is a plan change; built into a Quote (composition correctly locked to match the subscription); pushed through real Manager→Admin approval; confirmed the old subscription flipped to `CANCELLED` with the cross-referencing note and a brand-new `ACTIVE` one exists on the new cycle, both visible together in the company detail view.

### 10. Nav tab alert dots
User's request: on any interface, when content in a tab updates (negotiations, subscription changes, etc.) show a small dot on that nav tab so the user knows to check it.

### 12. Shipping location + Groq-assisted cost-optimized warehouse split
User's request: let the customer enter a shipping location when creating an order (one-time or recurring), and use Groq to pick/split warehouses to minimize shipping cost, rather than the existing placeholder (fill whichever warehouse has the most stock on hand). The schema's `QuoteItemAllocation.estimatedShippingCost` field already had a comment anticipating exactly this as a "later phase," so this closes that loop.

- **Schema migration** (`20260906160000_shipping_location`): `CustomerRequest.shippingLocation` / `Quote.shippingLocation` (both nullable `String`) - copied from request to quote at creation time, same pattern as `isRecurring`/`billingCycle`. Optional at the schema/API level (a plan-change request, say, doesn't collect one), but the "Create New Request" and "Recurring Plans" forms make it a required field of their own.
- **New `shippingAi.service.ts`**: asks Groq for a per-unit INR shipping-cost estimate from each candidate warehouse to the destination, given only city/region names - explicitly framed to the model as relative estimates for comparison, not real quotes. ### 23. Team Discussion - shared per-order comment thread
User's request: all internal teams should be able to communicate with each other via a common chatting interface, unique per order request, used to pass comments through to the roles evaluating that order.

- **Scoped to Quote, not CustomerRequest** - "order" already means Quote everywhere else in this app's own vocabulary (Reports' "Orders Under Review"/"Orders To Be Shipped" are both quotes), and unlike `CustomerRequest`, every order that goes through approval has one, including manually-started quotes with no request behind them. "Evaluation authorities" = the approval workflow (Manager/Finance/Admin), which operates on quotes, not requests.
- **Internal-only, deliberately excludes Customer** - "all the teams" reads as the internal departments (Sales/Manager/Finance/Admin) communicating about an order, not a customer-facing channel; the customer portal already has its own separate, structured Negotiations mechanism for customer↔Sales Rep back-and-forth, which this doesn't touch or replace.
- **New `OrderComment` model** (migration `20260906140000_order_comments`) - deliberately separate from `QuoteAuditEntry` (machine-generated, one row per approval-workflow action, always paired with a status change) since this is pure free-text human discussion with no workflow effect of its own: id, quoteId, userId, message, createdAt. One thread per quote.
- **New `orderComment.service.ts`**: `assertCanAccessQuote` reuses the exact same visibility rule as `quote.service.ts`'s `getQuoteForUser` (a Sales Rep sees only their own quote's thread; Manager/Finance/Admin see any) - not a new access model, just the existing one applied to a new resource. Mounted at `/api/quotes/:quoteId/comments` (mergeParams, same pattern as `recommendation.routes.ts`), gated to `SALES_REP, MANAGER, FINANCE, ADMIN` only.
- **New `TeamDiscussion.tsx`** component (message list + text input, polls every 8s - no websocket infra in this app, and an internal discussion thread doesn't need one) embedded wherever a quote's detail already renders: `QuoteBuilder.tsx` (Sales Rep's own view), `ApprovalDetail.tsx` (Manager/Finance/Admin's evaluation view), and `DealHealthDetail.tsx` (Manager/Admin's flagged-deal review) - all three point at the same `quoteId`, so it's genuinely one shared thread reachable from every angle, not three separate ones. Kept visually plain (bordered message blocks, sender name + role badge + timestamp) rather than chat-bubble styling, consistent with this app's established "premium enterprise, not consumer app" design language.
- **Scope cut, noted deliberately**: no nav-alert-dot integration for new messages - there's no natural top-level tab to attach one to (the thread is embedded inside existing detail pages, not its own tab), and building "has this been read" tracking for it felt like more than was actually asked for.

- `tsc -b` / `oxlint` / `vite build` clean on both sides.

### 24. Grievances - customer delivery complaints, Manager/Admin resolution queue
User's request: new customer-facing "Grievances" tab listing delivered orders, letting the customer raise a complaint about one via a small form, which lands in an alerts section directly below the internal Dashboard (Manager/Admin only), where staff interact with the customer through a message/forum-style thread until the customer themselves marks it resolved.

- **"Delivered orders" = the customer portal's own terminal order status**, same reasoning as feature 22's invoice PDFs: there's no separate shipping/delivery-tracking state anywhere in this schema, so "delivered" is treated as `Quote.status === APPROVED` - the customer portal's own `deriveOrderStatus` already collapses everything to IN_PROGRESS/APPROVED/CANCELLED and shows APPROVED as the customer's terminal "done" state. Scoped to `CustomerRequest`-based orders (same universe "My Orders" already shows) - a manually-started quote was never something the customer sees as "their order" to begin with.
- **New `Grievance`/`GrievanceMessage` models** (migration `20260906160000_grievances`) - `Grievance.quoteId` is `@unique`, deliberately making this a one-time flow per order ("click an order, raise a grievance," not an ongoing reopenable ticket) rather than allowing multiple grievances per order over time. `GrievanceMessage` is the forum-style back-and-forth after the initial description, same shape (sender name + role) as feature 23's `OrderComment`.
- **Resolution is explicitly the customer's call, not staff's** - there is no staff-side "resolve" endpoint anywhere in this feature; `grievance.service.ts`'s `resolveGrievance` is only ever reachable via the customer-portal route, guarded (`updateMany({where: {status: OPEN}})`) the same race-safe way every other status transition in this app is. Once `RESOLVED`, `addMessage` rejects further posts from either side - resolution is a hard stop, not something either party silently reopens by posting again.
- **Split router, shared service** (same pattern as `recommendation.routes.ts`'s internal-vs-customer split): customer-portal routes under the existing `/api/portal` router (`delivered-orders`, `grievances`, `grievances/order/:quoteId`, `grievances/:id/messages`, `grievances/:id/resolve`) and a new internal-only `grievance.routes.ts` at `/api/grievances` gated to **Manager and Admin only** - never Sales Rep or Finance, per the user's explicit ask (verified live: both get a flat 403). Both sides call the same `grievance.service.ts` functions; `addMessage` takes an `Actor` (id/role/customerId) and only enforces the one check neither route's role-gate already covers - a customer may only message their own grievance.
- **New `GrievanceAlerts.tsx`**, embedded directly below the shared Dashboard (`Dashboard.tsx`), gated to `MANAGER`/`ADMIN` only - exactly where the user asked for it, not a new SalesNav tab. Lists every grievance across every customer/Sales Rep, clicking one opens `GrievanceDetail.tsx` at `/sales/grievances/:id` (deliberately *not* listed in `SalesNav.tsx`'s `TABS` - only reachable from the Dashboard alert, matching "added directly below the dashboard screens" literally).
- **New customer pages**: `CustomerGrievances.tsx` (`/portal/grievances` - sortable/filterable list of delivered orders, per feature 13's shared hooks, each showing a grievance status badge or a "Raise Grievance" prompt) and `CustomerGrievanceDetail.tsx` (`/portal/grievances/:quoteId` - shows the raise-grievance form when no grievance exists yet for that order, or the full message thread + reply box + "Mark Resolved" button once one does). ## Key Technical Patterns (reusable across features)

- **Transaction staleness bug** (hit and fixed twice): calling a plain-`prisma` read function from *inside* an uncommitted `prisma.$transaction(async (tx) => {...})` returns stale data (different DB connection). Fix: do all writes via `tx`, call the plain-`prisma` read function only *after* the transaction promise resolves. Applied in `cancelMyOrder`, `decideTierChangeRequest`.
- **Migration workflow**: edit `schema.prisma` → `npx prisma migrate diff --from-url "postgresql://postgres:postgres@localhost:5432/dealflow360?schema=public" --to-schema-datamodel ./prisma/schema.prisma --script` (preview) → write the same diff into a new `prisma/migrations/<timestamp>_<name>/migration.sql` → `npx prisma migrate deploy` → kill the running dev server (find PID via `netstat -ano | grep ":4000" | grep LISTENING`, confirm it's the `tsx watch` process via `Get-CimInstance Win32_Process`, `Stop-Process -Force`) → `npx prisma generate` (fails with EPERM while the dev server holds the query-engine DLL open) → restart `npm run dev`.
- **Expandable table rows**: React `Fragment` with an explicit `key` inside `.map()` (shorthand `<>` fragments can't carry keys) — used for every "click a row to expand detail inline" table across the app.
- **Test-data cleanup discipline**: verify live via curl with real demo logins (`customer@dealflow.demo`, `sales@dealflow.demo`, `manager@dealflow.demo`, `admin@dealflow.demo`, all password `Demo@1234`), then clean up. Prefer direct SQL cleanup (via a `.sql` file written to the scratchpad dir, run with `psql.exe -f <file>` — inline `-c` SQL quoting is unreliable; `psql.exe` lives under `C:\Program Files\PostgreSQL\<version>\bin\` - check which version's actually installed, don't assume; also drop `?schema=public` from the connection string for `psql` itself, it's a Prisma-only query param) **except** when a quote has live warehouse reservations, in which case the real reject/release endpoint must be called first (to correctly decrement `Inventory.quantityReserved`/`quantityAvailable`), with SQL cleanup only for what's left afterward. For a quote with real generated Subscriptions/Invoices (an `APPROVED` test quote), delete in FK order: `subscription_events` → `invoices` → `subscriptions` → `quotes` (cascades items/allocations/audit entries) → `customer_requests`.
- **Customer-safe sanitization discipline**: all customer-facing quote/request data flows through `sanitizeQuote.ts`, which is extended carefully to expose only what's needed (e.g. `customerRequestDiscountReview`) without ever leaking internal-only fields (cost, margins, etc.).
